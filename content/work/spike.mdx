<p className="caps">The problem</p>

NASA publishes thousands of bioscience papers: radiation biology, plant growth in microgravity, the microbial census of the ISS. Almost none of it is queryable in the way a working researcher would want. Title-and-abstract search misses the protocols. Full-text search drowns you in noise. The interesting question is not *can we search PDFs* but *can we extract a consistent schema across them* without losing the rows that do not fit.

SPIKE answers that for a 600-paper subset: extract experimental conditions, organism, payload, and outcome into a typed record, validate aggressively, and route anything that fails into a human-reviewable queue.

Each PDF passes through OpenAI structured outputs against a hand-authored zod schema. The schema is deliberately narrow: eight fields, three of them enums. A narrow schema makes failure a signal, not noise. About 11% of papers failed validation on first pass; almost all of them were genuinely off-spec, and the dashboard surfaces them as a separate corpus.

<p className="caps">Key technical decisions</p>

- **zod over Pydantic.** Validation runs on the Next.js edge, so the schema needed to live in TypeScript. Authoring it once and exporting the inferred type to the API layer removed an entire class of drift bugs.
- **Dead-letter queue, not silent drop.** The single most useful design decision. Invalid rows are first-class data with their own UI surface, not log lines nobody reads.
- **Flask for the ingest worker.** Python has the better PDF and embeddings ecosystem; the ingest worker is the one place the productivity gap is real.
- **Citation graph as a static table, not a graph database.** 600 nodes, around 4k edges; a recursive CTE in Postgres outperforms anything I would have set up in a week.

<p className="caps">What I would do differently</p>

The schema is too narrow for review papers, which are a real research artifact, not just noise. I would ship a second schema variant rather than excluding them. I would also pull validation out of the ingest worker entirely and run it as a separate service. The coupling between "extract" and "decide if extraction is good" turned out to be a debugging anti-pattern.

I would also stop treating the LLM as a single trustworthy box. The second pass, a much cheaper model re-validating the first one's output, caught about 30 silent errors and would have caught more if I had wired it up earlier.
